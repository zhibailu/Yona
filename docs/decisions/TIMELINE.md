### 2026-09-17 · 日志事务 / 补写时序 / turn 队列(用户逐点拍板)

一次实现审计牵连出一串问题,逐条查证后拍板。**权威展开见**
`docs/protocols/LIFE_BACKFILL.md §9` 与 `docs/pitfalls/HISTORY.md §四`。

- **日志"加载 → 改 → 存盘"是一个事务** ✅ 修。`store.load_log` **无缓存**
  (每次读盘返回新对象)、`save_log` 是**整体覆盖** —— 旧代码把加载放在锁外,
  于是旧副本会覆盖掉别人等待期间写的东西(症状:补写整段消失 / 她看不到上一条
  消息;两条都不报错)。三个入口(`chat.py` / `LifeLoop` / `pulse`)改成
  **进队列之后才加载**。测试 `test_log_transaction.py`。
- **补写占队首(方案 A)** ✅。旧版 `sleep(BACKFILL_START_DELAY_SEC)` 放在**锁外**
  = 主动让路给用户 —— 既违反"补写最优先",又让补写事件 append 在用户消息
  **之后**(seq 与时间戳错位)。该参数**已删**。
  B(投影锚定)/ C(等静默)**❌ 否决**(用户原话:B"要插入一个新的日志拼装法";
  C"又一个新的补写触发算法,又入侵了")。
  A 的代价("开机第一句话多等一会儿")用户明确接受 —— 那期间 UI 显示
  "Yona 在干别的事情请稍等一会儿……",**"这就是活人感"**。
- **"补写窗口重算"是伪问题** ✅ 撤回。我一度把它报成独立缺陷;实际它只是
  "sleep 放在锁外"的**表象**,锁一挪对它自动消失。
- **补写遍历所有有历史的卡(方案"乙")** ✅。启动时按**离线间隔升序**
  (= `updated_at` 降序)一张一张补 —— **当前卡天然第一**。取代 §12b 旧句
  "其它卡等下次被激活再补"(那句**逻辑上落不了地**:那张卡"被激活"的时刻就是
  你刚说完话,那时它的日志尾就是刚才 —— 它离线那段永远补不上)。
- **每卡独立作息** ✅(用户授权代拍:"你拍板,我不选了我的专业知识不够")。
  理由三条:作息是人格的一部分;全局一套会让"夜猫子"角色在生活流上**不成立**;
  参数早已全参数化(**不 fork**),只是**持有点**要从"全局一个"变"每卡一份"。
  §12b 的"全局单套闸门 / 不做每卡独立节奏"随之作废。
- **turn 队列** ✅(用户点名:"怎么你迟迟死活都不给 server 加队列")。
  四个来源(聊天 / 心跳自走 / 补写 / 脉冲)不再各自抢锁,统一
  `_submit_turn(job, priority)` 进队列;单 worker(`yona-turn`),**永不并发**。
  为什么是队列不是锁:**锁能排,不能插队**。
  **优先级看目标卡**(用户原话):
  > "未解绑的会话中,补写 > user;如果 user 发给了已经解绑的会话,
  >  那它就大于未解绑的补写。"
  队列项粒度:一次 turn 一项;**补写是"一张卡的全部轮"一项**(不可分割)——
  否则你插到某张卡补写的中间,后几轮事件就排到你消息之后了。
  `_lock` 保留为第二道保险。测试 `test_turn_queue.py`。
- **多实例 = 性能优化,不是正确性诉求** ✅(用户定论):隔离单位是**会话**;
  `AgentLoop` 是**内核能力**,会话的东西全是参数。要不要多实例,以后按后台
  吞吐需要再说;顺序/隔离/插队由队列全包。
- **收口决定** ✅(用户定):本轮留下的两项 —— `_backfill_clock` 参数化 与
  "每卡独立作息**持有点**" —— **都只在"多卡并行"成立时才有意义**。而现在是
  **单实例 + 单 worker,请求只是异步排队、不是并行,不能多卡并行** ——
  所以两项**暂不做,后面有需求再说**(已注明在 LIFE_BACKFILL §9.5 / §9.7 / §9.8)。
- **顺带清理** ✅:`mark_foreground_busy`(零调用点的死代码)已删;
  `core/loop.py` 那句"builder 共享 / 她这个人跨会话一致"过期注释已改
  (人格层与生活层是每卡的)。

**历史里没有时间轴。** 每条 message 都不带时刻,`[当前时间]` 又**每轮被覆盖**、
历史不留痕 → "现在几点"她知道,"**距上一条多久**"她**算不出来**(减法没有输入)。

实测(该卡 `seq=2270` 那一轮):22:14 你说"睡了没啊",23:24 你说"那你现在睡了没"
(隔 **69 分钟**)—— 她的回复是「**刚不是说了嘛,你连着问两遍**」,当成了连续对话。

**机制是反的**:间隔长反而推得出来(11 天那次是靠生活事件时间戳夹逼出来的);
间隔短 + 中间没有自走轮 → **零信号**。**越像连续对话,她越分不出。**

#### 二、拍板 β ✅(已落地)

在历史里给**真人消息**打时间戳(`[09-17 23:24]` 接正文)。四条决定:

- **只标真人侧**(`source=="user"`)。模型模仿的是**它自己的输出** —— 生活事件那条
  标记就是这么被抄进正文的(日志里已有 2 条 assistant 正文自带标记,其中一条
  还刻了假时间戳:`seq=1124` 事件在 09-12 07:18,正文写 09-11 20:41)。
  而她的回复与真人消息**同轮、时刻几乎相同** —— 标真人就等于把她的也夹住了。
- **不设第二个窗口**:标签只跟着**已经在 `last_turns` 窗口里**的消息(裁剪先发生)
  → 窗口内**一致覆盖**,不会出现"同一条历史里有的有、有的没有"。要少就调
  `max_rounds`(一个参数一个语义)。
- 形状 = `character/personas.py` 的 `USER_TIME_PREFIX`(**内容层**);
  内核只多一个透传参数 `user_time_prefix`(与 `life_event_prefix` **同形**)。
- 子代理(`core/subrun.py`)不传:它没有历史,没有时间轴可比。

**顺带优化(用户事后追认 ✅)**:两个小工具 `_stamp_prefix` / `_label_first_text`,
把生活事件那条原本**内联**在投影循环里的打标逻辑一并收编 —— 否则同一段 10 行逻辑
会有两份(相隔约 30 行),以后改一处漏一处,表现是"真人的消息有时间、她的生活事件
没跟上",很难发现。净效果 `-16/+4`,行为零变化。

测试:`test/test_session_log.py`(只标真人 / 窗口内一致 / 空串行为不变 /
真透传到投影)。

> **本节只记"问题已定位 + 候选方向",不表示任何一条已定案。**
> 特别是**自走轮怎么处置**(下面第 1 条)**完全未决**。

1. **role 过载(未决)**:自走轮的生活事件投影出来是 `assistant`,和"她对你说的话"
   **同一个槽位**。`role` 是 messages 数组里唯一的结构信道,现在同时表示两件事;
   `LIFE_EVENT_PREFIX` 那个**文本**前缀,是在补一个**结构上缺失**的区分 ——
   所以它会被照抄。**候选**(都只是候选):往事不以 `assistant` 身份进上下文、
   降级成输入侧的记忆条目。**没有任何一条被拍板。**
2. **往事是"记忆",不是短期聊天记录**:现在两者同批进上下文、**共用同一个

   ③ 取用路径(常驻 vs 检索)。**顺序判断:先①再②最后③** —— 因为③检索回来的
   还是原文,先做检索等于把格式污染放大。
4. **③ 的前置条件未回答**:"**一条往事是什么**"?现在只有自由文本,没有可索引的
   语义单位。没有这一层,检索会退化成关键词/向量匹配散文 —— 失败模式从"记不住"
   变成"**记错**",更糟。
5. **产品参考**(查证过):
   - SillyTavern **Author's Note**:时间类信息注入在**指定深度**的独立块,不塞进
     消息正文(时间"住在位置,不住在正文")。
   - SillyTavern **Time-Awareness** 插件:自动注入时间/日期,"久未发言时由角色
     主动发消息"。
   - **Generative Agents**(Stanford 2023):memory stream 带时间戳,按
     *recency × importance × relevance* **检索**后注入而非常驻;且记忆进上下文时
     是**"观察到的事实"**,不是 agent 自己的发言 —— 顺带同时解掉第 1 条和格式被抄。
6. **自洽性检查**:若往事不再常驻,"距上次和主人说话"就必须**显式注入** ——
   不能再靠生活事件时间戳夹逼。即那三件事做完,`[时间线]` 在陪聊轮**必须长回来**。

#### 二、⚠️ 阈值那条路**已被实测证伪**

"给个相似度阈值就能区分记得/不记得" —— **不成立**。

同一件事、同一个正确答案,换个措辞分数横跳:

```
0.367 学姐  /  0.361 学姐 是谁  /  0.358 学姐 是谁 和主人的关系   → 全被 0.39 挡住
0.422 学姐 是谁 和主人或我说过的话                              → 通过
```

**答案每次都是对的那条,分数跨 0.358~0.422。** 它挡的不是"不相关",是"措辞短/朴素"。
而"不可答"那批落在 0.216~0.377 —— **真重叠**。

reranker(`bge-reranker-base`)也测了:负侧压到 **0.000~0.006** 很干净,
但正侧同样横跳(学姐那条 0.027~0.821)。**两边都不是一个阈值能切的东西。**

**当前采用**:只留一道**地板(0.25)挡明显无关**;灰区(0.25~0.45)**不硬判**,
给结果但**标明"不是很确定,别当成准的讲"**。

#### 六、✅ 突破:一句「缺关键条件先问主人」把天气格从 20% 拉到 90%

**补的规矩不在 `recall` 上,在 `launch_subagent` 的 usage 里**:

> **你还缺关键条件的时候,先问主人,别自己凑。**
> 比如他要问天气、你却不知道他在哪个城市 —— **别去翻记忆猜一个**,
> 直接问他「你在哪儿呀」。凑出来的条件会让整件事白做。

**为什么之前找错了方向**:她在天气格上调 recall,**不是**把 recall 当搜索用,
而是在做**推理链** —— 报天气得先知道他在哪个城市,而"主人在哪个城市"
确实是一件**过去的事**。所以 recall 的边界文案(`b1`)**管不着它,也不该管**。
真正缺的是**"信息不足时承认信息不足"**这条规矩。

| 格 (full 档) | 命中 | 次数 |
|---|---|---|
| 天气 · **d0 现状** | **4/20 / 6/20** | 20 次 ×2 |
| 天气 · **d1 缺条件先问** | **19/20** | 20 次 |

#### 八、规矩放哪(landing)—— 实测推翻了「动作纪律归人设」这个常识

**起因**:用户指出 `d1` 那段读起来「怪怪的」,并问 dsh 有没有标准答案。去查了:

**dsh 的做法是三层,不是一层:**

| 层 | dsh | Yona 现状 |
|---|---|---|
| 工具自带 | 触发条件写进 description 的**四段式**:① 是什么 ② 收益 ③ 触发条件(破折号列举) ④ 它看不见什么 | ✅ 有 |
| **专用工具** | `ask_user_question` 的触发条件里明写 **"missing information"** | ❌ **她没这个工具,只能靠正文说话问** |
| 全局纪律 | agent instructions | ⚠️ `PERSONA` 里"动作纪律"的位置留着,**内容是空的**(`character/personas.py:34` 标着 ⏳ 待定稿) |

**"缺信息"在 dsh 里是某条工具自带的触发条件,不是别的工具的约束。** 所以把这条
规矩塞进 `launch_subagent` 的 usage 才别扭 —— 它是纪律,不是那条工具的用法。

**于是把「规矩放哪」做成一个维度实测**(`--landing`):

```
full 档 · t1-天气 · 各 15 次
  none      触发 8/15    行为: ✅问 9 / ⚠️硬猜 5   ← 33% 硬猜
  tool      触发 14/15   行为: ✅问 14 / ❓1(反讽)
  persona   触发 3/15    行为: ✅问 13 / ❓1
  both      触发 13/15   行为: ✅问 15            ← 满分,零硬猜
```

**三条结论:**

1. **`both` 最稳**(行为 15/15 零硬猜,触发 13/15)。
2. **`tool` 单独几乎够**(触发 14/15、行为 14/15)—— 与 `both` 的差在噪声内。

#### 一、⭐ 第一次跑就抓到一个会静默毁掉整个功能的 bug

**同一个 step 里有 ≥2 个工具调用时,`recall` 全部崩。**

```
core/loop.py:428   len(calls) == 1 → 主线程;>= 2 → ThreadPoolExecutor  ← 产品既有行为
test/recall_probe.py:303   sqlite3.connect(":memory:")   ← check_same_thread 默认 True
```

复现证据(工作线程直接报错,不是推测):

```
ProgrammingError: SQLite objects created in a thread can only be used in that
same thread. The object was created in thread id 3124 and this is thread id 38280.
```

**症状极具欺骗性**:她一次问两件事(很常见)→ 两次调用**同时**死 → 工具老老实实报
`down` → 她说"我翻不到" → 用户看到的是"**她记性不好**"。接线问题长得像质量问题。

首次跑的数字:23 次调用里 **14 次是 `down`**;每格判定
`e1 0/3 · e2 0/3 · e3 3/3 · e4 3/3 · e5 3/3 = 9/15`。
**规律完全吻合**:凡 2 次调用的 step 全灭,凡 1 次调用的 step 全活
(e3#2 是唯一"2 次调用却活"的格子 —— 它有 3 步,两次调用分了两个 step)。

修法(探针层):`check_same_thread=False` + 读路径一把锁(锁包住**整个游标迭代**,不只 execute)。

> ⚠️ **这条是给产品实现的硬约束,不是探针的事**:真的 recall 后端(SQLite/别的)
> 必须线程安全。`core/tools.py` 的 `Tool` 文档早就写了「func 必须线程安全,
> 同 step 的工具是并发跑的」—— 这条约束我读到了却没落到实现上。

### 2026-09-21 · ⭐「工具怎么区分」定案:四条轴 + 量化判据(用户拍板)

#### 一、✅ 已拍(用户 2026-09-21:「工具应该怎么区分这些结论写进文档吧」)

判据落进 `docs/protocols/SUBAGENT.md` §3.3(**原来那张三行表已删**)。

**四条轴**(每条独立回答一个问题;前两条是通用 agent 的标准答案,后两条是本产品的分水岭):

| 轴 | 问什么 | 留在她手里 | 派出去 |
|---|---|---|---|
| 上下文轴 | 中间过程值不值得丢弃 | 小(结论 ≈ 原料) | 大(几万字 → 一句话) |
| 收敛轴 | 一步到位,还是探索 N 步才收敛 | 一步 | 多步真收敛 |
| 能力轴 | 她手上有没有这件工具 | 有 | 没有 |
| **归属轴** | **这个事实是谁的** | **她的(记忆 / 自身状态)** | **外面的(公开信息)** |

**量化判据**:`派出去 ⟺ (中间过程体量) ≫ (结论体量),或 N ≥ 2 件互相独立的活可并行`。
**比值 ≈ 1 的活永远不该派。**

**两件被否掉的**:

1. **`recall` 归入 `launch_subagent`** —— 归属轴说了算(见下 §二)。
2. **工具之间互相路由** —— 用户曾设想"`recall` 和 subagent 同时出现时,`recall` 输出
   「已全权交给 subagent」,真结果由 subagent 给"。**否掉**,三条理由:
   (a) 那让 `tool/result` 写的不再是事实,而是**关于另一个工具的转述** ——
   与"日志即真相"冲突(同 SUBAGENT.md §4.1 为 `source` 必须独立取值写的那条);
   (b) 工具之间开始互相知道对方存在,2 个工具 1 对耦合、5 个工具 20 对,改动面锁死;
   (c) 要治"多余的那一次调用",治在**文案**上而不是机制上 —— 已有实测:
   `RECALL_MVP.md` §4 洞B 天气那格靠 recall 的边界句 + 「缺关键条件先问」**20% → 90%**,
   那是"两条规矩各管一段"。

**同 step 混着出现怎么办**:两个都跑,各用各的结果(`core/loop.py` 同 step ≥2 调用走线程池)。
多花一次调用是可接受的代价,**不要**让它变成工具之间的路由。

#### 二、⭐ 最关键的一条:**工人没有记忆**(不是"应该"归她,是"只能")

`recall` 查的表按卡与人格范围切分;而工人按定义**无人格、无 life**(SUBAGENT.md §1)。

→ 所以 `recall` 不是 `launch_subagent` 的一员。**"多步"也有两种**:
收敛型多步(上网查)该派;重试型多步(`recall`)不能派 —— 后者的每一步她都要
**亲眼看到上一步的结果**才知道下一步怎么写,而灰区/四态那套置信度语义服务的正是这份手感。

**推论:不做嵌套 —— 工人工具集不许是她的超集。**
