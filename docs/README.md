# 文档总索引(docs/README)

> Yona 2.0 的分层文档地图:谁放哪、读的顺序、状态标记。
> 目标:不再把所有东西挤进一两个根文件;每个话题有自己的一份,每份标状态。
> 阅读入口 = 本文件 → 相关子目录 → 目标代码模块头部注释。

---

## 状态图例(全文统一)

| 标记 | 含义 | 用法 |
|---|---|---|
| ✅ | 用户拍板(带日期) | 事实,可依赖 |
| ⏳ | 待拍(未定) | **禁止给默认 / 禁止当已定使用** |
| ⏸ | 延后 / 冻结 | 暂不做,留入口或注释 |
| ❌ | 否决(弃稿) | 别再用 |
| 🔧 | 开发/演示参数,非产品语义 | params.py 专用 |

## 文档分层(按"嵌在项目各处"放)

```
yona-rewrite/
├─ AI-GUARDRAILS.md            · AI 边界 + 矛盾登记 + 守则(开工先读)
├─ core/README.md              · 内核目录自己的文档
├─ server/README.md            · 服务层目录自己的文档
├─ character/README.md         · 角色层目录自己的文档
├─ docs/README.md              · 本文件(地图/图例)
├─ docs/decisions/             · 设计拍板(ADR 式: id/日期/状态/原话/影响)
├─ docs/tasks/                 · 任务安排 / 进度 / 开放项(⏳ 归这里)
├─ docs/pitfalls/              · 踩坑与教训(含"AI 与用户意志冲突"类)
└─ docs/protocols/             · 模块协议/算法(如 life 事件采样协议)
```

## 根目录旧文档(正典,迁移前不动;迁一个退一个)

| 文件 | 现状 | 去向(渐进拆) |
|---|---|---|
| VISION.md | 愿景/拍板方向 | 部分 → docs/decisions |
| DESIGN.md | 设计决策/取舍 | → docs/decisions |
| STRUCTURE.md | 结构(含陈旧矛盾:git init/_life/行数待清) | → docs + core/server/character README |
| MAP.md | 进度 + 拍板时间线 + 开放项(已挤成一个杂物袋) | 拍板→decisions;进度→tasks;待拍→tasks |
| LIFE_BACKFILL.md | 生活补写协议 | → docs/protocols |

**当前真值排序**(拆完前照这个,别照陈旧的):MAP 最新拍板 → params.py(✅/⏳)
→ personas.py(内容层文案)→ 代码头部注释。

## 每个 .py 头注释的约定

- 模块头注释写"这个文件是什么、放什么"；
- 涉及产品语义的参数/开关,标 ✅(已拍)或 ⏳(待拍),不写死结论；
- 如果一份长期文档要为某模块单独存在,进 `docs/protocols/<模块>.md`,模块头链过来。

## 写新文档的规则(防再乱)

1. 一个话题一份文件,别往已有杂物袋里续写;
2. 拍板记录:必须含 **日期 · 你的原话/要点 · ✅/⏳ · 影响**;
3. 我(AI)推断的范围标"(待确认)",不冒充拍板;
4. 发现旧文自相矛盾 → 新建/并入 `docs/pitfalls/`,报用户,不默默二选一。
