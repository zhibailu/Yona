## 0. 一页速览

- **没有多层继承。只有两层。** 深度只可能来自"嵌套的执行体",而递归子代理**已砍**。
- **两条正交的轴**:能力轴(工具在这里,相交/只减)与角色轴(人设在这里,覆盖/就近赢)。
  **两轴不相交 = "工具与角色解绑"的确切含义。**
- **L2 的判定键不是 `source` 本身** —— 自走轮和补写轮共用 `source="self"`,靠 `time_cursor` 区分。
- **"加"与"减"是两条通道**:减 = allow/deny 相交;加 = 在自己这一层注册。

---

## 1. 结论:两层

```
L1  全局            进程注册表的全部工具（基线）
       │
L2  轮次种类        一个键，查出「身份 + 模式 + 工具可见性」
       │
       └  narrow    叶子：现场临时收窄（不是层，不留痕）
```

**为什么只有两层**:层的唯一判据是**存在嵌套的执行体**。
- 会话不是层 —— 它不发起 LLM 调用,只是"写到哪个文件"。
- 卡不是层 —— 它是**产品形态**,在**角色轴**上,不碰工具(见 §2)。
- 模式(陪聊/自走/补写)不是层 —— 它和"身份"是**同一个键的两个返回字段**,同级。

**深度的唯一来源 = 子代理再派子代理。** 已砍(`SUBAGENT.md` §7),所以深度恒为 2。

---

## 2. 两条正交的轴

```
轴一 · 能力轴（工具在这里：相交，只减不增）
    L1 全局 ──► L2 轮次种类 ──► narrow（叶子，现场）

轴二 · 角色轴（人设在这里：覆盖，就近赢）
    卡 ──► 角色设定快照 ──► 当轮覆盖
    （性格 / 身份背景 / 语气 / life / 日志 / 图片）
```

**两轴不相交 —— 这就是"工具与角色解绑":**

- 轴二怎么改(性格从温柔改成毒舌、背景改成社畜),**轴一不动**:能用的工具依旧是那一套。
- 轴一怎么改(给自走轮少开几个工具),**轴二不动**。

> **卡 = 一整整个产品形态**(用户 2026-09-15 原话:「所谓的"一张卡"在我这的重要程度就等于一个产品」)。
> 它管的是"她这个人是谁、过着什么日子" —— **它不管工具**。她是谁,和她能不能上网搜,是两件事。

> 附注:用户明确说过**不会做"专门干劳动的通用 agent"那种产品形态**。所以"卡"只有一种,
> 不存在"陪伴卡 / 劳动卡"的分型;工人是**内部执行单元**,不是一张卡。

## 3. L2 的判定键(实测更正)

**键不是 `source` 一个字段。** 现状实测(`server/app/engine.py`):

| 轮次 | `source` | 还靠什么区分 | 身份 | 工具(现状) |
|---|---|---|---|---|
| 陪聊 | `"user"` | — (`chat.py` 调用点) | 她 | 她的工具集 |
| 自走(心跳/脉冲) | `"self"` | — | 她 | 她的工具集 |
| **补写(离线回放)** | **`"self"`** | **`log.time_cursor is not None`** | 她 | **空注册表** |
| 压缩摘要 | `"compact"` | `session_log.replace()` | — | — |
| 用户编辑 | `"user-edit"` | `store.py` | — | — |
| **工人(计划中)** | **`"subagent"`** | — | 工人 | 只读白名单 |

**两个要点:**

1. **补写轮和自走轮共用 `source="self"`。** 靠 `source` 一个键**分不开它们**。
   补写轮的工具差异目前是**在调用点硬传**的(`engine._maybe_backfill_life`
   里传 `tools=empty_tools`),
   装配差异靠 `log.time_cursor` 判定 → 选 `_composers["backfill"]`。
   → 所以 L2 的键应当是一个**派生出来的"轮次种类"**,`source` 是它的主要输入,但不是全部。
2. **现状是"调用点显式传 `tools=`"**,不是"照表路由"。本协议要做的就是把这条现状
   收成**一张表**,让"谁看得见什么"有一个单一落点。

## 5. 加 / 减两条通道

| 通道 | 语义 | 效果 |
|---|---|---|
| **减**(`allow` / `deny`) | 层与层**相交** | **只减不增 → 下层绕不过上层** |
| **加**(在自己这一层**注册**) | 新增工具 | 只对本层及以下可见 |

**"幽灵能力进不来"不成立** —— 因为加法走注册通道,永远允许:

- "这个能力只有工人有" → **在工人那一层注册它**,进得来。
- "上层禁掉的东西,下层想开" → **永远不允许**,而且是故意的。

**判据一句话:减走禁令,加走注册;两条路不许混。**

## 6. 校对记录(避免重复踩)

本章前后连着错了四次,**都是同一个毛病:往树里塞层去凑数**。记下来防止再犯:

| # | 当时的说法 | 错在哪 |
|---|---|---|
| 1 | 会话是第 2 层 | ❌ 它不发起 LLM 调用,只是数据容器 |
| 2 | 卡是第 2 层 | ❌ 卡在**角色轴**上,做成层就违背"工具与角色解绑" |
| 3 | 模式是第 3 层 | ❌ 它与"身份"是**同一个键的两个字段**,同级;而且是为凑"至少三层"硬加的 |
| 4 | `BY_SOURCE` 按 `source` 建表 | ❌ **自走轮和补写轮共用 `source="self"`** —— 一个 source 键分不开(用户质疑"有补写这个 source 吗"才发现) |

**根因**:判据始终只有一条 —— **有没有"嵌套的执行体"**。没有嵌套,就没有深度。
4 个轮次种类是**宽度**(条目多),不是**深度**(层多)。
