## 0. 一页速览

**一句话**:子代理 = **工人身份的 loop 复用**。不是第二个她,是一个由她派出去、
不带人格、会死、不进主日志的一次性执行单元。

**三条存在意义**:隔离 · 并发 · 调度。

**一条硬约束**:`core/loop.py` 的 turn 锁**不可重入** —— 所以只能复用 loop 的
**构造与装配**,不能复用 loop 的**实例**。详见 §2.3。

**哪件活归谁**:见 §3.3 的划分线(四条轴 + 量化判据)。一句话 ——
**她的记忆与自身状态归她,外面的公开信息归工人**,两条轴不重叠,所以工人工具集
**不是**她的超集,也不需要工具之间互相路由。

## 1. 身份:工人,不是第二个她

| | 谁在跑 | 日志 | 人格 | 生命周期 | 谁触发 |
|---|---|---|---|---|---|
| 陪聊轮 | **她** | 主日志 | 有 | 活着 | 真人 |
| 自走轮 | **她** | **主日志** | **有**(+自走情境段) | **活着** | 时间 + 闸门 |
| **子运行** | **工人** | **独立日志** | **无** | **会死** | 她的工具调用 |

**子运行明确不是这些**:

- 不是第二个她 —— 拿不到 persona,拿不到 life,不参与心跳/闸门/自走;
- 不写主日志 —— 主日志只留 `tool/call` + `tool/result`(带 `run_id` 血缘);
- 不会做梦 —— 跑完即止,没有"活着"这个状态。

> ⚠️ 为什么身份不能松:dsh 的子代理是"**继承父的预设**,再叠加可选的人格遮盖"
> (`child-agent.d.ts`:`join its parent's preset … then apply the child's own
> shadowing persona section`)。那条路对通用 agent 成立,对陪伴体不成立 ——
> 一旦分身也有她的人格,主日志里"她说的话"和"分身说的话"就分不开了,
> 而"她是一个人"是 VISION 决策 6/7 的根。

## 2. 复用范围(写死:复用什么,不复用什么)

### 2.1 复用

| 复用对象 | 说明 |
|---|---|
| **循环代码** | `core/loop.py` 的 `AgentLoop` —— 逐字复用,不写第二个循环 |
| **日志原语** | `core/session_log.py` 的 `SessionLog` —— 每个子运行一份新的 |
| **工具原语** | `core/tools.py` 的 `Tool` / `ToolRegistry` —— 同一套实现,白名单不同 |
| **LLM 客户端** | 同一个 `LLM` 协议 —— 换个实例就换了档位(弱模型实验的接口) |
| **装配机制** | `core/composer.py` 的段装配 —— 按 `source` 路由到不同装配(§4) |

### 2.2 不复用

| 不复用对象 | 原因 |
|---|---|
| **loop 实例** | turn 锁不可重入,见 §2.3 |
| **主日志** | 隔离的全部意义所在 —— 脑内过程不进她的记忆 |
| **persona / 情境段** | 它不是她 |
| **turn 锁** | 她一次只做一件事;**工人不占这条不变量** |
| **life / 心跳 / 闸门** | 它不会活着 |

### 2.3 硬约束:必须新实例

```python
# core/loop.py
self._turn_lock = threading.Lock()      # 不可重入
def run_turn(...):
    with self._turn_lock:               # ← 工具执行发生在这把锁**之内**
        return self._run_turn_locked(...)
```

工具调用是在 `_run_turn_locked` 内部发生的,也就是**已经握着锁**。
此时在工具里再调同一个实例的 `run_turn` = **当场死锁**。

→ **每个子运行一个新的 `AgentLoop` 实例**,共享 llm / composer builder / 工具实现。
装配复用了,锁不撞。

### 2.4 为什么"单次 LLM 就能做的活"也要用 agentloop

这是本设计的**预设立场**(用户 2026-09-15 原话:「虽然这些任务可能单独调用一次
llm 就能完成了用不上 agentloop,但同样用 agent 完成是因为架构正确」)。

买到的不是"更强的能力",而是**同一套基础设施**:

- 同一套 loop、同一套装配路由、同一套预算、同一套日志与可观测;
- 任务哪天变复杂(要多步、要工具、要重试),**不用换范式**;
- 只有一个执行原语要维护,而不是"轻任务走这里、重任务走那里"两套。

## 3. 存在意义:隔离 · 并发 · 调度

### 3.1 隔离(三层)

| 层 | 隔什么 |
|---|---|
| 人格 | 子运行拿不到 persona,只有任务级 SYSTEM |
| 日志 | 它的全过程不进她的日志;主日志只有两行 |
| 工具 | 白名单 —— 没给它的工具**从它的 prompt 里消失**,也拒绝执行 |

### 3.2 并发 + 规模

**一次可以发出去多个子代理** —— 这是它作为独立原语(而不是"同步函数调用")
的核心价值,直接推出**队列**:排队 / 并发上限 / 状态 / 取消。

⚠️ **规模问题是真的**:并发意味着成本与故障面同时放大。没有累计预算之前,
"一次发出去很多个"是一句空话。见 §4.3。

### 3.3 调度:主 loop 保持专注

用户 2026-09-15 原话:「它可以切分掉大部分的 tool 不在主 loop 明文显现,
主 loop 对话的时候能够非常专注,需要 tool 的时候就打开 subagent,
subagent 代它去看 tool。当然主 loop 不是完全不留 tool 了。」

**划分线 ✅ 2026-09-21 定案**(此前是本文件的推断,标着"待确认"):

原来那张三行表(**本次已删**)是**第一版推断,信息不全** —— 它只有"上下文"这一条轴,所以
`recall`(只读、要好几步、结果是原料)按它会**整行落在"派出去"那一列**,
而主产品语义说它必须留在她手里。冲突的根因是:那张表把**四条独立的轴**压成了一条。

#### 四条轴(每条独立回答一个问题)

| 轴 | 问什么 | 留在她手里 | 派出去 |
|---|---|---|---|
| **上下文轴** | 中间过程值不值得丢弃 | 小(结论 ≈ 原料) | 大(几万字网页 → 一句话) |
| **收敛轴** | 一步到位,还是探索 N 步才收敛 | 一步 | 多步真收敛 |
| **能力轴** | 她手上有没有这件工具 | 有 | 没有 |
| **归属轴** | **这个事实是谁的** | **她的(记忆 / 自身状态)** | **外面的(公开信息)** |

**通用 agent 的标准答案只覆盖前两条轴。** 它们判"要不要派"只看上下文经济学 ——
中间过程是噪音就隔离掉(Claude Code 的子代理文档、Anthropic 的工具设计文都是这个理由)。
那两条对陪伴体**不全**,后两条才是本产品与通用 agent 的分水岭。

#### 量化判据(可查)

> **派出去 ⟺ (中间过程的体量) ≫ (结论的体量),或者有 N ≥ 2 件互相独立的活可并行。**

**比值 ≈ 1 的活永远不该派** —— 付一整份额外 SYSTEM + 额外一步 + 序列化,
换回的是同一坨字,还多绕一层。

这条**能解释**已有实测(不是新实验,出处 `character/tools.py:113-121` 的三轮实验):
"她做不了的活" 64/64 派(比值 ∞);"她做得完的长活" 6/52 —— **那正是比值接近 1 的一格**,
所以换任何措辞都推不动。那不是文案失败,是那一格本来就不该有偏好。

#### "多步"有两种,长得一样但不该同样处理

- **收敛型多步**(上网查):每一步拿到新信息、方向在收窄、中间过程可丢弃 → **该派**。
- **重试型多步**(`recall` 实测最多 4 步):没找着 → 换个说法再试。**每一步她都要亲眼看到
  上一步的结果**,才知道下一步怎么写 → **不能派**。把这段交出去,她只拿回一句结论,
  就失去了"我的手感" —— 而灰区 / 四态那套置信度语义,服务的正是这份手感。

#### 归属轴的决定性一条:工人没有记忆

`recall` 查的表按卡与人格范围切分;而工人按定义**无人格、无 life**(§1)。
要让它能查,就得给它同一份记忆访问权 —— 那等于亲手拆掉 §3.1 的"人格层隔离"。

→ 所以 `recall` **不是** `launch_subagent` 的一名成员。它不是"应该"归她,是**只能**归她。
同理,改她自身变量的工具(`change_outfit` 一类、以及将来的健康 / 好感度)同样只能在她手里。

#### 不做嵌套:能力归属唯一

**工人工具集不许是她的超集。** 同一个能力有两个家,模型就必须回答"这件事**在哪做**",
而这个问题的正确答案**不存在**(两边都对),只能比成本 —— 而模型看不见成本。
她的决定应该永远只有"**用不用**",从来没有"**在哪用**"。

这条同时说明:`TOOL_VISIBILITY.md` §5 的"加通道"(在自己这一层注册工具)**有前提** ——
先由本节定完"这件能力归谁",才轮到注册它。

**现状符合这条**:网络两件只注册进工人(`engine._worker_tools`),她手上**一件网络工具都没有**,
所以"她自己也能查天气"这个前提今天不成立,没有重复。

#### 同一个 step 混着出现时:不路由、不代转

直接调用与委派同时出现,**两个都跑,各用各的结果**(`core/loop.py` 同 step ≥2 调用走线程池,
两个结果都会回来)。多花一次调用是可接受的代价 —— 不要让它变成工具之间的路由。三条理由:

1. **工具结果会撒谎。** 若 `recall` 的返回里写「已全权交给 subagent」,它写的不再是事实,
   而是**关于另一个工具的转述**。这与本项目的根(日志即真相)冲突 ——
   同 §4.1 为 `source` 必须独立取值写的那条。
2. **工具之间开始互相知道对方存在。** 2 个工具 1 对耦合,5 个工具 20 对,而且改动面互相锁死。
3. **要治"多余的那一次调用",治在文案上,不是机制上。** 已有实测:
   `docs/decisions/RECALL_MVP.md` §4 洞B —— 天气那一格靠 `recall` 的边界句
   + 本工具那句「缺关键条件先问」,**20% → 90%**。那是"两条规矩各管一段",
   不是"一个工具替另一个路由"。

**行业参照**(说明本文件为什么不能照抄通用 agent 的划分):
dsh 的子代理是"**继承父的预设**,再叠加人格遮盖"(`child-agent.d.ts`);
那条路对通用 agent 成立,对陪伴体不成立,理由见 §1。

### 3.4 能力预期与规模边界(明确不做什么)

**我们不做完整的一套 subagent。** 别人的子代理能扛多步复杂任务,因为它们的
loop 基础设施本身就能循环得很好;我们的 loop 现在很薄,一轮往往一两个 step 就结束。

**本设计的定位**:子代理专门用于**简单的 LLM 任务 + 多个 LLM 任务并发** ——
总结一篇文章、websearch 完再整理格式、其它零散小任务。

**明确不做**(⏸ 挂起):

- 子运行再派子运行(不做递归,就不需要深度守卫);
- 持久化子会话 / 冷恢复;
- 复杂多步编排 / 工作流。

## 5. 与自走的关系:平行,不是包含

用户 2026-09-15 提问:「这个设计下是不是它的等级又高一层,之前的自走周期
是不是也被它囊括并且需要收束进去了?」

**答:不能并入,但能共享三层。**

- **不能并入** —— 自走是**她在跑**(她的身份、她的日志、她的记忆),子运行不是她。
  把自走并进子代理 = 把"她活着"降级成一个工人,正面砍在 VISION 决策 6/7 的根上。
- **能共享**:

| 层 | 现状(两套) | 应收束为 |
|---|---|---|
| 调度 / 准入 | 闸门决定"起不起自走轮";队列准入决定"起不起子运行" | 同一件事:**小成本规则决定要不要起活** |
| 预算 | 自走用**时间预算**(分钟,只为叙述);子运行要 **token 预算** | 一套统一的预算原语 |
| 工具策略 | 各自为政 | 一套"无人看守时的工具可见性"策略 |

**另一条新性质(⏳ 待异步落地后才成立)**:异步子运行开了之后,"她一次只做一件事"这条不变量**只管她,
不管工人** —— 系统第一次出现"她在说话的同时,旁边有别的活在跑"。这不是冲突,是设计。
(今天 `engine._run_worker` 仍是阻塞语义,"她一次只做一件事"这条不变量暂时还在全量生效)

> 【2026-09-21 23:15 标 · ⏳ 未落地】上面这条性质写成现在时,读起来像**已经发生** ——
> 真相:`server/app/engine.py:149-156` 的 `_run_worker` docstring 写着「**阻塞**是 v1 的语义:
> 她这一轮会等它跑完」;异步投递 = 本文件 §7 任务栏的任务 5,未开工。
