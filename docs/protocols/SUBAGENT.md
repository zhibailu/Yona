## 0. 一页速览

**一句话**:子代理 = **工人身份的 loop 复用**。不是第二个她,是一个由她派出去、
不带人格、会死、不进主日志的一次性执行单元。

**三条存在意义**:隔离 · 并发 · 调度。

**一条硬约束**:`core/loop.py` 的 turn 锁**不可重入** —— 所以只能复用 loop 的
**构造与装配**,不能复用 loop 的**实例**。详见 §2.3。

---

## 1. 身份:工人,不是第二个她

| | 谁在跑 | 日志 | 人格 | 生命周期 | 谁触发 |
|---|---|---|---|---|---|
| 陪聊轮 | **她** | 主日志 | 有 | 活着 | 真人 |
| 自走轮 | **她** | **主日志** | **有**(+自走情境段) | **活着** | 时间 + 闸门 |
| **子运行** | **工人** | **独立日志** | **无** | **会死** | 她的工具调用 |

**子运行明确不是这些**:

- 不是第二个她 —— 拿不到 persona,拿不到 life,不参与心跳/闸门/自走;
- 不写主日志 —— 主日志只留 `tool/call` + `tool/result`(带 `run_id` 血缘);
- 不会做梦 —— 跑完即止,没有"活着"这个状态。

> ⚠️ 为什么身份不能松:dsh 的子代理是"**继承父的预设**,再叠加可选的人格遮盖"
> (`child-agent.d.ts`:`join its parent's preset … then apply the child's own
> shadowing persona section`)。那条路对通用 agent 成立,对陪伴体不成立 ——
> 一旦分身也有她的人格,主日志里"她说的话"和"分身说的话"就分不开了,
> 而"她是一个人"是 VISION 决策 6/7 的根。

## 2. 复用范围(写死:复用什么,不复用什么)

### 2.1 复用

| 复用对象 | 说明 |
|---|---|
| **循环代码** | `core/loop.py` 的 `AgentLoop` —— 逐字复用,不写第二个循环 |
| **日志原语** | `core/session_log.py` 的 `SessionLog` —— 每个子运行一份新的 |
| **工具原语** | `core/tools.py` 的 `Tool` / `ToolRegistry` —— 同一套实现,白名单不同 |
| **LLM 客户端** | 同一个 `LLM` 协议 —— 换个实例就换了档位(弱模型实验的接口) |
| **装配机制** | `core/composer.py` 的段装配 —— 按 `source` 路由到不同装配(§4) |

### 2.2 不复用

| 不复用对象 | 原因 |
|---|---|
| **loop 实例** | turn 锁不可重入,见 §2.3 |
| **主日志** | 隔离的全部意义所在 —— 脑内过程不进她的记忆 |
| **persona / 情境段** | 它不是她 |
| **turn 锁** | 她一次只做一件事;**工人不占这条不变量** |
| **life / 心跳 / 闸门** | 它不会活着 |

### 2.3 硬约束:必须新实例

```python
# core/loop.py
self._turn_lock = threading.Lock()      # 不可重入
def run_turn(...):
    with self._turn_lock:               # ← 工具执行发生在这把锁**之内**
        return self._run_turn_locked(...)
```

工具调用是在 `_run_turn_locked` 内部发生的,也就是**已经握着锁**。
此时在工具里再调同一个实例的 `run_turn` = **当场死锁**。

→ **每个子运行一个新的 `AgentLoop` 实例**,共享 llm / composer builder / 工具实现。
装配复用了,锁不撞。

### 2.4 为什么"单次 LLM 就能做的活"也要用 agentloop

这是本设计的**预设立场**(用户 2026-09-15 原话:「虽然这些任务可能单独调用一次
llm 就能完成了用不上 agentloop,但同样用 agent 完成是因为架构正确」)。

买到的不是"更强的能力",而是**同一套基础设施**:

- 同一套 loop、同一套装配路由、同一套预算、同一套日志与可观测;
- 任务哪天变复杂(要多步、要工具、要重试),**不用换范式**;
- 只有一个执行原语要维护,而不是"轻任务走这里、重任务走那里"两套。

## 3. 存在意义:隔离 · 并发 · 调度

### 3.1 隔离(三层)

| 层 | 隔什么 |
|---|---|
| 人格 | 子运行拿不到 persona,只有任务级 SYSTEM |
| 日志 | 它的全过程不进她的日志;主日志只有两行 |
| 工具 | 白名单 —— 没给它的工具**从它的 prompt 里消失**,也拒绝执行 |

### 3.2 并发 + 规模

**一次可以发出去多个子代理** —— 这是它作为独立原语(而不是"同步函数调用")
的核心价值,直接推出**队列**:排队 / 并发上限 / 状态 / 取消。

⚠️ **规模问题是真的**:并发意味着成本与故障面同时放大。没有累计预算之前,
"一次发出去很多个"是一句空话。见 §4.3。

### 3.3 调度:主 loop 保持专注

用户 2026-09-15 原话:「它可以切分掉大部分的 tool 不在主 loop 明文显现,
主 loop 对话的时候能够非常专注,需要 tool 的时候就打开 subagent,
subagent 代它去看 tool。当然主 loop 不是完全不留 tool 了。」

**划分线(待确认)**:我没有单独拍过这条线,以下是我的推断,用户未逐条确认:

| 留在主 loop(她手里) | 派出去(工人代她去看) |
|---|---|
| 有副作用的动作 | 只读、探索性的 |
| 瞬时的、她要当场感知的 | 要好几步才收敛的 |
| 她用来判断"要不要派"的依据 | 结果是一坨原料、她要的只是结论 |

### 3.4 能力预期与规模边界(明确不做什么)

**我们不做完整的一套 subagent。** 别人的子代理能扛多步复杂任务,因为它们的
loop 基础设施本身就能循环得很好;我们的 loop 现在很薄,一轮往往一两个 step 就结束。

**本设计的定位**:子代理专门用于**简单的 LLM 任务 + 多个 LLM 任务并发** ——
总结一篇文章、websearch 完再整理格式、其它零散小任务。

**明确不做**(⏸ 挂起):

- 子运行再派子运行(不做递归,就不需要深度守卫);
- 持久化子会话 / 冷恢复;
- 复杂多步编排 / 工作流。

## 4. 装配策略

### 4.1 `source` 是路由键

装配不是"新机制",是**加一个 `source` 值**。`core/loop.py` 的 SYSTEM builder 签名
本来就是 `(registry, source, log)`(arity 2/3),`server/app/engine.py` 已经按
`source` 决定 persona 与时间源 —— **加一个分支,隔离的设置点就现成了**。

```
source="user"       → 旗舰装配(persona + 世界 + 状态 + 时间线 + 她手里的工具)
source="self"       → 旗舰装配 + 自走情境段 + 时间预算(同一份 persona)
source="subagent"   → 任务级 SYSTEM,无 persona、无情境段、白名单工具   ← 本协议新增
```

**`source` 必须是它自己的值,不许复用 `"user"`。** 理由:

1. 本项目的核心是**日志即真相**,`source` 存在的全部意义就是记来源。库里已有
   三个先例:`self`(自走)、`compact`(摘要顶替)、`user-edit`(编辑);
   `subagent` 是第四个,不给值才是例外。
2. 实打实的后果:子运行自己的日志若标 `"user"`,`make_timeline_section`
   (`core/composer.py`:判 `source == "user"`)会算出"距上次真人互动 X 分钟"
   —— **那是句谎话**。

**`source` 的现成消费点**(加新值时必须一起看):

| 位置 | 用途 |
|---|---|
| `core/loop.py` `run_turn` | 写进 `turn/start` 与 `user/message` |
| `core/loop.py` | `source == "self"` → user 槽放占位串 |
| `core/loop.py` `_system_text` | **路由到 SYSTEM 装配**(本协议的主落点) |
| `core/session_log.py` | `self_turns` 投影 / 已结束轮跳过自走占位 |
| `core/composer.py` | 时间线的"最后一次真人互动"锚点 |
| `server/store.py` | 会话列表 / life 流的过滤 |

### 4.2 该看到什么 / 不准看到什么

| 项 | 给不给 |
|---|---|
| persona | ❌ |
| 她的状态段(穿着等) | ❌ |
| 世界时钟段 | ⏳ 待定(子运行要不要知道"现在几点") |
| 时间线段(距上次真人互动) | ❌(对工人无意义) |
| 任务书 | ✅(进它的 user 槽) |
| 工具 | ✅ 白名单(空 = 无工具) |

### 4.3 预算(**2026-09-15 实测,这是本设计最硬的一条**)

**事实**:`server/params.py` 的 `LLM_OUTPUT_MAX_TOKENS = 4096` 是**拍给聊天轮的**,
且它作用在**每一次调用**上;**产品里没有任何累计预算**(全仓库无实现)。
推理模型的 `reasoning_tokens` **计入** `output_tokens`。

**实测**(2026-09-15,`deepseek-v4-flash` / `deepseek-v4-pro`,同一"整理长文本"任务):

| 预算 | 模型 | 结果 | 输出 | 其中推理 |
|---|---|---|---|---|
| 4096 | flash | **failed / max-tokens,正文 0 token** | 4093 | 4093 = **100%** |
| 8192 | flash | completed(29.9s) | 6184 | 5522 = 89% |
| 8192 | pro | completed(146.1s) | 6784 | 6353 = 94% |

**结论**:4096 对这个活**不是"紧",是"不可能"**;而"输出预算"实际上几乎
全是**思考预算**。

**待拍(⏳)**:子运行的单次预算取多少?要不要独立成档(不借聊天轮的值)?
累计预算(按活 / 按轮 / 按天)设不设、设多少?

### 4.4 工具策略

"无人看守时哪些工具可见" —— 自走轮和子运行**共用一套策略**,不各写各的。

**形态已对齐(2026-09-15)**:见 [`TOOL_VISIBILITY.md`](./TOOL_VISIBILITY.md) ——
两层结构(全局 → 轮次种类)、两条正交轴(能力轴 / 角色轴)、
**减走禁令·加走注册**、深度只来自嵌套执行体(本协议不做递归 ⇒ 恒为两层)。

⏳ 仍待拍:四个轮次种类**各自放哪些工具**(见 `TOOL_VISIBILITY.md` §4)。
⏳ 另见:`TOOL_VISIBILITY.md` §3 实测发现 —— **自走轮与补写轮共用 `source="self"`**,
所以判定键不能只用 `source`,必须派生出「轮次种类」。

## 5. 与自走的关系:平行,不是包含

用户 2026-09-15 提问:「这个设计下是不是它的等级又高一层,之前的自走周期
是不是也被它囊括并且需要收束进去了?」

**答:不能并入,但能共享三层。**

- **不能并入** —— 自走是**她在跑**(她的身份、她的日志、她的记忆),子运行不是她。
  把自走并进子代理 = 把"她活着"降级成一个工人,正面砍在 VISION 决策 6/7 的根上。
- **能共享**:

| 层 | 现状(两套) | 应收束为 |
|---|---|---|
| 调度 / 准入 | 闸门决定"起不起自走轮";队列准入决定"起不起子运行" | 同一件事:**小成本规则决定要不要起活** |
| 预算 | 自走用**时间预算**(分钟,只为叙述);子运行要 **token 预算** | 一套统一的预算原语 |
| 工具策略 | 各自为政 | 一套"无人看守时的工具可见性"策略 |

**另一条新性质**:异步子运行开了之后,"她一次只做一件事"这条不变量**只管她,
不管工人** —— 系统第一次出现"她在说话的同时,旁边有别的活在跑"。这不是冲突,是设计。
