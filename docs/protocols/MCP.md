## 1. 拍板:不自研适配层,直接用现成的 MCP server

**用户 2026-10-08 20:35 原话口径**:

> 「MCP这件事当初已经大概了解完了,至于具体加哪些不急着管,主要是确认了,
> 我们大概率**不自己造MCP**了,都用**MCP本身代表的 N×M 的便捷性**去加载,方向是这样的。」

即:**要为 Yona 接外部能力时,不手写"某家 API → 我们的工具形状"的适配层,
而是消费别人已经做好的 MCP server。**

**为什么是这个方向**:MCP 存在的唯一理由是 **N×M → N+M** ——
N 个模型 × M 个工具,原本要写 N×M 份对接,有了统一形状就只要 N+M。
类比是**插座/USB 口**:电器侧做统一插头,不必为每个插座重新拉一根线。
MCP server 就是那个**适配器**:把某家 API 的形状翻译成 MCP 的统一形状,
它本身不创造能力、不改变任何东西。

## 2. 判据:三者的真正区别不在"远近",在**循环在哪里闭合**

这条是那轮讨论最值钱的产出。同样是"调外部能力",有三种形态:

| | 谁执行 | 几段 | 结果经过谁 |
|---|---|---|---|
| **本地工具** | 你(客户端进程) | 1 段 | 全回来 |
| **MCP** | 外部执行体(另一个进程/机器) | **2 段** | **前两段都经过你**(你是翻译官) |
| **server tool**(如 `web_search_20250305`) | 对方机房 | 1 段(你只剩端点) | **绕过去了** |

**判据不是物理距离,是循环在哪里闭合。** MCP 的循环**必须回到客户端进程**
—— 因为 **MCP server 里没有模型**(实证:`@modelcontextprotocol/server-github`
的依赖只有 sdk / node-fetch / universal-user-agent / zod,没有任何模型客户端)。
而 server tool 的循环**在对方机房里就闭合了** —— DSH 的 `mapAnthropicResponse`
在同一次响应里就同时拿到 `web_search_tool_result` 块和最终 `text` 块,
说明"搜完了"这件事在返回给你之前已经发生完了;若是客户端工具,对方只会回
`stop_reason: "tool_use"` 且**零结果**。

> ⚠️ **不要在"能力层"上争定义**:功能上 MCP 与 server tool 可以完全一样,
> server tool 还更方便(不用起进程、不用管凭证)。**要说的是"少了什么"** ——
> MCP 那两段经过你,所以你能记账、能拦、能改;server tool 那段绕过去了,
> **你就只能看到一个结果,看不到过程,也没法插话**。

## 3. MCP 的必要件(1 + 1 + 1 + 3 + 2)

只有这些,多一个都不需要:

| 件 | 是什么 |
|---|---|
| **1 管道** | stdio:进程的 stdin / stdout / stderr。**stdout 只走协议**,一个字节的调试输出都不能混进去 |
| **1 信封** | JSON-RPC 2.0,一行一个 JSON |
| **1 规矩** | **有 `id` = 请求,要回应;没 `id` = 通知,不回应** |
| **3 动词** | `initialize` / `tools/list` / `tools/call` |
| **2 形状** | 工具 `{name, description, inputSchema}`;结果 `{content: [块...]}` |

**编码也是协议的一部分**,不只是字段名 —— 规范为 stdio 传输钉死 UTF-8,
就是因为跨进程边界后,两边对"一个中文字符占几个字节"的默认假设不一致。

## 4. 三处容易踩的形状差异

### 4.1 同一个字段,三家三个名字

| 一方 | 字段名 |
|---|---|
| MCP | `inputSchema` |
| OpenAI / DeepSeek | `parameters` |
| Anthropic | `input_schema` |

外加一层**结构重排**:OpenAI 把 `name` / `description` 往下挪一层,
包成 `{type: "function", function: {name, description, parameters}}`。

**主导这个变化的是客户端**(即"翻译官")—— 因为两边都不知道、也不需要知道
对方的口音。**这个变化不可省略**:`inputSchema` 原样丢给模型,模型不认。

### 4.2 工具名"加壳/拆壳"

模型看到的名字是 **`mcp__<serverName>__<rawName>`**;发给 MCP server 时
**必须拆回裸名**(协议里根本没有 `mcp__` 这个概念)。

加壳的三个好处:① 命名空间隔离(两个 server 都提供 `search` 时不会撞);
② 与内置工具名隔离;③ **名字必须是 `(serverName, rawName)` 的纯函数** ——
README 明确写「连接顺序、重新同步和其他服务器永远不会重命名工具」,
因为**重命名会让 KV 缓存失效**(「从第一个变化的 schema token 起的复用失效」)。
类比:**门牌号**,不是排队号。

### 4.3 一次调用的"六跳",中间有三处打包/拆包

```
① 你 → 模型      名字 mcp__github__list_commits + parameters(JSON 对象)
② 模型 → 你      同名,但 arguments 是一个**字符串**
③ 你 → MCP server 名字拆成 list_commits,arguments 是对象
④ MCP server → 你  content 块数组,真数据塞在一个 text 字符串里(实测 8363 字符)
⑤ 你 → 模型      tool_call_id 必须与 ② 对得上
⑥ 模型读到的是对方 API 的原始结构(约 95% 是噪音)
```

## 5. 用现成 MCP server 的代价(买的是什么)

**方向是对的,但"用现成的"不等于"无脑装"。** 三条代价:

| 代价 | 具体是什么 |
|---|---|
| **多一个第三方进程** | 它是**另一个程序**:要装、要起、会挂。实测 `server-everything` 第一次 `tools/list` 返回 **0 个工具**,等 3 秒才是 13 个(异步注册)—— 这正是 `notifications/tools/list_changed` 与客户端的重同步机制存在的原因 |
| **凭证落在你机器上** | 例如 GitHub 那个 MCP server 的工具里,**能"以你的身份"建仓库、推文件、合 PR**(`create_repository` 的原文是"Create a new GitHub repository **in your account**")。它不是在"读",它是在"当你" |
| **每个 server 都吃 schema token** | 工具定义要进模型上下文。GitHub 那个装了 **26 个工具**(12 写 / 14 读) |

**挑选原则(未拍,供讨论)**:优先选**只读**、工具数少、凭证权限最小的 server;
"能手"类的(能写、能推、能以你身份行动)一律要单独过一遍。
