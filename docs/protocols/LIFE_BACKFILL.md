## 1. 核心算法:连续概率判定(§10,用户拍板)

### 1.1 期望的定义(纠正两轮后的最终形态)

否决过 λ(t) = 期望事件/小时(速率,隐含"长度×λ");最终定为:

> **连续概率判定**。一条可微概率曲线 rate(t),程序从 last_active 到 now
> 按固定粒度逐格点伯努利判定:命中概率 = rate(t)·Δt。
> 命中 → 生成事件;不中 → 下一格点。**期望事件数 = ∫ rate(t) dt**
> (曲线下面积,可微积分预计算:"7~9 点预期 0.8 件")。

- 粒度:默认**分钟级**(13h ≈ 780 格点,<1ms);秒级 ≈ 47k、~5ms 也可接受。
- 概率含义:rate(t) 是"该时刻生成事件的概率密度",不是件数速率。

### 1.2 正交:rate(t) = K × shape(t)(用户明确要求的两个独立旋钮)

```
rate(t) = K × shape(t)
  shape(t): 归一化曲线(∫shape = 1)—— 只定"事件爱在几点出"(形状)
            (睡眠窗 23:30-06:30 为 0:在睡,不判定)
  K:        总期望件数 —— 只整体缩放,不改变形状
期望件数 = K·∫shape(窗口)  ← 件数与形状无关(正交)
落点分布 = shape(t)        ← 形状与件数无关
```

- K 已拍板固定 = **1.5**(不随长度放大)。
- 长度如何影响件数:通过"窗口覆盖了多少 shape 面积"——
  覆盖全天醒着(∫shape=1) → 期望 = K;只覆盖稀疏段 → 期望小;
  48h(两个白天)≈ 2K。**不是长度本身卷进期望**,是位置在起作用。

### 1.3 事件与预算(用户拍的语义)

- 命中后抽 **budget**(时长分布,分钟)。作用三件:
  ① 给模型当上限("这段时间约 X 分钟,只做一件事、别做做不完的事");
  ② 跳过 budget 内的格点(这段时间她在做那件事,不再判定 —— 天然产生空档);
  ③ 算相对时间。
- **budget 不进日志** —— 事件只有**起始时间 + 内容,无终止时间**。
- **一个时间段 = 一件事**(模型每段只产一件,prompt 强调)。
- 被睡眠窗 / 区间终点截得不足 5 分钟的事件不硬凑(丢弃,继续判定)。

### 1.4 结束条件(用户上一条纠正)

不是"时间撞到 now 才完",而是**判定序列走到"不再有判定机会"为止**:
例如只给过 8 点一次判定、没中,后面即使名义上还有一小时预算,但
没有判定点就不会再出事件,没有可消费的了,直接结束。

### 1.5 相对时间(用户定义)

`next.start − (prev.start + prev.budget)` = 两件事之间**空档**(不是两个
start 相减)。gap > 60s → 当轮提示"距上一件事做完已过约 X";否则
"刚做完不久"。只当轮可见,不进日志。

## 3. 架构:收编(无第二 AgentLoop)

补写轮 = **普通自走轮**:`_loop.run_turn(source="self", log=<目标卡 log>,
tools=ToolRegistry([]), self_note=note)`。她只有一个大脑 —— 差异只在
**log 有没有时间游标**:

| | 普通轮(心跳/脉冲/自走) | 补写轮(回放) |
|---|---|---|
| log 时间游标 | 无 → 墙钟 | 有 → 世界时间 = 历史时刻 |
| 事件时间戳 | 墙钟 | 落历史时刻 |
| 情境 | SELF_SITUATION(独处轮) | **复用同一份 SELF_SITUATION**(2026-09 情境合一,曾另写 BACKFILL_SITUATION 已删) |
| 世界时间(world section) | 墙钟 | `_backfill_clock["ts"]`(每 step 现取) |
| tools | 全量(可换装) | 空(`ToolRegistry([])`:补写是"那段日子怎么过的") |

> 2026-09 补充(普通轮同款,与补写对齐):普通自走/心跳/脉冲用同一条
> LifeSampler 对 [日志尾→当前] 采样出预算,无事件 → 安静结束不调 LLM;
> 事件轮"当前时间 = 事件 start"的锚定**只留 lab**,不改产品输出。

### 3.2 启动链路(server/app/engine.py)

> 2026-09-17 校正:本节此前写的是**旧的全局生活流版**(`_last_active_anywhere`
> / "她这个人跨会话一致"),已被 §12b 每卡 life 取代。下为**当前真实链路**
> (以代码为准:`_maybe_backfill_life` / `life_session_id`)。

```
start()(lifespan 调一次)
 └─ _maybe_backfill_life()                    # 只在这一处被调用
     └─ 后台线程 "yona-backfill" ─► **立刻抢 _lock**,以下**全在锁内**:
         ├─ life_session_id()                 # = store.life_target_session_id()
         │                                    #   「最近激活的卡」= updated_at 最新
         │                                    #   且日志里有真人 user/message 的卡
         │                                    #   (没聊过任何卡 → Yona 旗舰兜底)
         ├─ card_log = load_log(sid)
         ├─ last_active = 该卡日志尾事件时间
         ├─ _wake_decision(last_active, now)  # 纯函数:首启不补 / gap<30min 正常重启
         │                                    #   / gap≥30min → 补写;不触发则直接返回
         ├─ LifeSampler(last_active, now).sample() → events[]
         ├─ 若无事件 → 跳过(离线太短/稀疏/没判定中,正常)
         ├─ snap = 该卡快照的人格覆盖(有则用)
         └─ 逐事件:
             ├─ 组 self_note(预算上限 + gap_note)
             ├─ card_log.set_time_cursor(e.start); _backfill_clock["ts"] = e.start
             ├─ _loop.run_turn(source="self", log=card_log, tools=空, self_note, system_prompt=人格)
             └─ finally: clear_time_cursor(); _backfill_clock["ts"] = 0.0
         收尾: save_log(sid, card_log) → _life_gate.mark_self()(进入心跳冷却,节奏衔接)
```

**2026-09-17 方案 A**:锁外**只剩"起线程"这一件事** —— 从"读日志尾"开始
(那是决策依据)到"跑完 N 轮",一气呵成在同一把锁里。旧的
`sleep(BACKFILL_START_DELAY_SEC)`(锁外让路给用户)已删,理由见 §9.3。

- **补哪些卡(2026-09-17 ✅ 已拍,方案"乙")**:**遍历所有有历史的卡**,按
  **离线间隔升序**(= `updated_at` 降序)一张一张补 —— **当前卡天然第一**。
  这取代了 §12b 旧句"只补'最近激活的卡';其它卡等下次被激活再补"(那句
  **在逻辑上落不了地**,见 §9.6)。
  未解绑的卡会进 `_pending_backfill`:期间发给它的 user 请求排在它的补写
  **后面**;已解绑的卡,user 请求插到所有未解绑补写**前面**。
- 事件之间日志历史累积 → 逐段叙事连贯自发涌现(不需要显式桥接)。
- `_backfill_clock` 只在回放轮内被设;补写 composer 的 world section 现取它
  (模型看到的时间 = 历史时刻,墙钟不混入)。**它是进程级全局** —— 多卡并发时
  会串台,见 §9.4。

## 4. 采样器实现(server/rhythm.py)

```
public:
  SHAPE_TABLE / DEFAULT_K / DEFAULT_DURATION_MIX / GRID_SEC / MIN_EVENT_SEC
  density_at(hour, table=None)        线性插值(未归一化)
  ShapeCurve(table=None)              ∫=1、睡眠窗=0;构造时缓存归一化常数 z
  DEFAULT_SHAPE                       默认候选曲线
  shape_at(hour) / rate_at(hour,k)    K×shape(件/小时 = 命中概率密度)
  integral_shape(h0,h1)               ∫shape(h1 可跨天)
  Event(start, budget_min)            end = start+budget 只是统计用派生属性
  LifeSampler(t0, t1, *, rng/seed, K, shape/shape_table, duration_mix)

sample() 逐格点:
  t 从 t0 走到 t1,格长 GRID_SEC:
    睡眠窗内 shape=0 → 永不命中(自然跳过)
    否则 命中概率 = K·shape(h)·(GRID_SEC/3600)
    命中 → 抽 raw budget → end = min(t+budget, t1, 下一个睡眠窗起点)
          end−t ≥ 5min 才记 Event(start=t, budget_min=(end−t)/60)
          然后 t = end(跳过该段);否则 t += 格长
  判定机会耗尽(t ≥ t1)即结束
```

- 睡眠窗截断:23:00 命中、抽到长 budget,名义消费裁到 23:30 前
  (她"要做也会在睡前做完",不给模型"睡两小时"的怪上限)。
- 全部随机走注入 rng/seed → 单测、固定复现。
- 模型零时间权力:事件在几点出、预算多少全由采样器定;模型只拿 start。

### 5.3 观测到的输出特征(2026-09 真模型多样本)

### 9.1 三个缺口

| ① | 「其它卡等**下次被激活**再补」没实现 | `_maybe_backfill_life()` 全项目只被 `start()` 调一次(`engine.py`),只检查 `life_session_id()` 那一张卡。⚠️ 该承诺**在逻辑上就落不了地**(不是"没写"),见 §9.6 |

### 9.2 根因一句话

> **补写的语义是「你不在时她的生活」。你的消息一进日志,那段生活就结束了。**

于是正确性要求是:

> **补写事件必须落在「你出现」之前。**

① ② ③ 都是这一条被破坏的不同表现:① 没触发,② 触发晚了,③ 同时触发多张卡。

### 9.3 ✅ 已修:根因是「锁的位置」,不是「窗口算早了」

> 2026-09-17 用户指出。先前我把"补写窗口重算"报成一个独立问题 —— **那是错的**,
> 修正见 §9.4 末。

`BACKFILL_START_DELAY_SEC` 原意是"等服务起来 + **防抢用户首条消息**"
(`params.py` ⏳ 沿用值)。但它把 sleep 放在了**锁外**:

```
旧:start() 读日志尾+判断(无锁) ─► 起线程 ─► sleep 5s【锁外!】─► 抢锁 ─► 跑 N 轮
                                             ↑
                         这 5 秒里用户消息先拿锁、先落盘
                         → 补写事件 append 在你后面(seq 与时间戳错位)

新:start() 起线程 ─► 【立刻抢锁】─► 读日志尾 → 判断 → 采样 → 跑 N 轮(一气呵成)
                         ↑
                    你排在门外;补写跑完你才进 → 顺序天然正确
```

**"让路给用户"和"补写最优先"是直接冲突的** —— 用户拍板选后者,该参数已删。

**关键约束**(已写进 `engine.py::_maybe_backfill_life` 的 docstring):

> **一张卡的全部补写轮 = 一个不可分割的队列项(turn 队列)。**
> 从"读日志尾"开始 —— 那是**决策依据** —— 到"跑完 N 轮 → 落盘",必须一气呵成。
> 依据和基于它的动作之间一旦松手,依据就可能过期。
> 你插队只能插在**整张卡**的前面或后面,**不会插到它中间**。

### 9.4 方案候选 —— **A ✅ 采用;B / C ❌ 否决**

#### ✅ 方案 A · 补写占队首(采用)

补写线程**起来就去抢 `engine._lock`**,抢到后一口气做完:
读日志尾 → 判断 → 采样 → 跑完 N 轮 → 落盘 → 释放。

| | |
|---|---|
| ✅ | 语义最直:**"她补完日子,才轮到你说话"**;日志 seq 与时间序天然一致,**无需任何新机制** |
| ✅ | 与用户原话一致:"进程重启级别的补写轮,物理上就是最优先级的" |
| ⚠️ | 启动后**首条消息要等补写跑完**(N 轮 × LLM 延迟,粗估 30–90s) |
| ↳ | **该代价用户明确接受**:"多等一会儿"期间 UI 显示"Yona 在干别的事情请稍等一会儿……",**这就是活人感** |

> ⚠️ **修正(先前报错的方向)**:我一度把"补写窗口重算"当成 A 方案的**第一步**,

> **"窗口重算"整个是「sleep 放在锁外」的表象,不是独立缺陷。锁一挪对,它自动消失。**

### 9.5 ⏳ 潜伏的坑(#③):`_backfill_clock` —— **当前不会触发**,动多卡并行前必须先看它

> **2026-09-17 现状注明(用户定)**:**现在是单实例 + 单 worker —— 请求只是
> 异步排队,不是并行。** 所以同一时刻只有一张卡在补写,`_backfill_clock` 这个
> 进程全局**不会被串**。它是个**潜伏**的坑:**后面有需求(多卡并行)再说。**
> 本节保留,是为了让将来动并行的人**先看到它**,而不是重新踩一遍。

现在同一个信息存了**两份**:

```python
card_log.set_time_cursor(e.start)     # ← 挂在卡上 ✅
_backfill_clock["ts"] = e.start       # ← 挂在进程上 ❌
```

`log.time_cursor` 挂在 `SessionLog` 实例上是**对的**(每卡各带各的);
`_backfill_clock` 是模块全局,**一个副本服务多张卡**。

**卡住改动的只有一处**:补写 composer 的 `world_now` 闭包

```python
world_now=lambda: time.localtime(_backfill_clock["ts"])
```

它在 `_build_engine` 时造好,**拿不到 log、也不知道自己在服务哪张卡**。
另外两个读点(`_now(log)` 与 `sys_by_source`)**手里都有 log**。

**改法**:把世界时间当**参数**传进 composer(三参 builder 本来就收到 log),
或让 `world_now` 读 `log.time_cursor`;产品路径两者本就同时设成同一个值
(两个标志一起判是为了区分"真回放"和"实验台拨时间" —— 可换成显式标志)。

> 判据(记进 `docs/pitfalls/HISTORY.md §四`):**一个变量的值如果是「本卡的」,
> 它就不该住在模块全局。**

### 9.6 ⏳ 多卡触发点(①):启动时该补几张卡

> ⚠️ **撤回一个我自己搞错的方向。** 本节先前写的是"在聊天轮之前加触发点" ——
> 那把补写**绑到了用户消息**上,与"补写是程序自主行为"根本矛盾。用户点破后撤回。
>
> **补写的唯一触发时机就是进程启动**(`start()` → `_maybe_backfill_life`)。
> **用户消息永远不是补写触发点。**

于是 ① 的真问题不是"挂在哪",而是:**启动时检查几张卡。**

#### §12b 那句承诺实现不了(不是"没写",是逻辑上落不了地)

> "只补'最近激活的卡';**其它卡等下次被激活再补**。"

"被激活"= 你刚在那张卡里说了话(`store.life_target_session_id` 的定义:
`updated_at` 最新 **且** 日志里有真人 `user/message`)。

**可那一刻它的日志尾就是你刚说的那句** → 算出的 gap 是"刚才 → 现在" →
**它离线那段永远补不上。** 承诺落不了地。

```
9/10 你跟 A 聊、又跟 B 聊(B 成为"最近激活")
9/15 启动 → 补 B 的 [9/10, 9/15] ✓ ;A 那段 [9/10, 9/15] 没补
9/16 你切到 A 说了两句(A 变成"最近激活",但 A.tail = 9/16)
9/20 启动 → 补 A 的 [9/16, 9/20]
        → A 在 9/10–9/15 的空白**永远补不上** ✗
```

#### ✅ 已拍(2026-09-17):取**乙** —— 启动时遍历所有有历史的卡

用户原话:"多卡触发就**统一在进程重启的时候**和当下最前面的那个一起吧……
反正都是时间刻一下一下敲门的,不然还得确定别的卡的触发是绑 server 点开那个
会话还是别的东西,又得考量,很麻烦。"

| 规则 | 内容 |
|---|---|
| 触发时机 | **只有进程启动**;不绑任何别的触发点(尤其**不是**用户消息) |
| 补几张 | **所有**有真人 `user/message` 的卡(`_wake_decision` 自带"无历史不补") |
| 顺序 | **离线间隔升序**(= `updated_at` 降序)→ **当前卡天然排第一** |
| 粒度 | 一张卡 = **一个队列项**(见 §9.3) |
| 队列 | `_submit_turn(..., priority=_QUEUE_SELF)`;user 请求永远插在 self 前面 |

**效果**:开机后你等的是**当前卡**那一段,不是全部;之后你一发消息就插队到
所有剩余的补写项前面 —— "已经解绑的会话来了 user 请求,其余靠后被插队"。

> ⚠️ 一个仍待补的实现细节(不影响本拍板):窗口**终点**用"此刻"即可 ——
> 因为整张卡是不可分割的队列项,补写跑的时候没有别人能往这张卡的日志里写。
> 若队列上仍可能有别的卡并发(目前没有),才需要另行处理。

#### (历史)当时列出的两种选法

| | 做什么 | 代价 |
